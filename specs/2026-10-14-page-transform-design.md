# 페이지 변형과 이미지 삽입 설계 (D)

작성일: 2026-10-14

## 배경

`Page`는 `width`·`height`를 갖고 검증이 "유한하고 0보다 큼"만 요구한다
(`structure.rs:64-68`). 즉 **페이지 크기는 바꿀 수 있게 되어 있다** — 하지만 그것을
바꾸는 커맨드도, 바꿨을 때 자식들이 어떻게 되는지에 대한 규칙도 없다.

그리고 캔버스에 **외부 이미지를 넣는 수단이 없다.** 사용자가 참조 이미지·스크린톤·
말풍선 소재를 가져오려면 파일을 열어야 하는데, 그 경로가 없다.

D는 그 둘을 다룬다. 둘을 함께 다루는 이유는 **같은 좌표 문제**를 공유하기 때문이다:
페이지 크기를 바꾸면 자식들의 좌표를 어떻게 할지 정해야 하고, 이미지를 삽입하면
그 이미지의 픽셀을 페이지 좌표 어디에 놓을지 정해야 한다.

## 범위

| 덩어리 | 내용 |
|---|---|
| D1 | 페이지 크기 변경 (자르기·확장)과 리샘플 |
| D2 | 페이지 회전과 대칭(좌우/상하 뒤집기) |
| D3 | 이미지 삽입 (파일 → 새 래스터 레이어) |

구현 순서는 **D3 → D1 → D2**를 제안한다. D3이 가장 독립적이고(새 레이어 하나를
만들 뿐 기존 데이터를 건드리지 않는다), D1은 **모든 자식의 좌표**를 건드리며,
D2는 D1의 변환 골격을 재사용한다.

## 결정 사항

| # | 결정 | 근거 |
|---|---|---|
| D-D1 | 페이지 크기 변경은 **자르기(Crop)와 확장(Extend) 두 가지**이고, 내용을 옮기지 않는다 | "크기 변경"과 "내용 이동"을 한 동작으로 합치면 무엇이 일어났는지 설명할 수 없다. 자르기는 크기만 바꾸고(내용은 페이지 좌표에 그대로) 확장도 크기만 바꾼다. 내용을 옮기려면 이미 있는(또는 C의) 이동을 쓴다 |
| D-D2 | 자르기로 페이지 밖으로 나간 내용은 **삭제하지 않는다.** 좌표가 음수가 되어도 살아 있다 | 삭제하면 되돌리기로도 복구할 수 없는 데이터 손실이다. 페이지 밖 내용은 그려지지 않지만 남아 있고, 확장하면 다시 보인다. 이것이 "자르기 = 뷰포트 변경"이라는 일관된 모델을 만든다 |
| D-D3 | 래스터 자산의 리샘플은 **명시적 선택**이다. 기본은 리샘플하지 않는다 | 자동 리샘플은 픽셀을 영구히 바꾸고, 사용자가 원하지 않았을 수 있다. 기본(비리샘플)은 원본 픽셀을 보존하며, 페이지가 커지면 여백이 생기고 작아지면 잘린다 — D-D2와 같은 모델이다. 사용자가 명시적으로 요청할 때만 리샘플한다 |
| D-D4 | 회전은 **90도 단위**만 지원한다 | 임의 각도 회전은 리샘플을 강제하고(D-D3과 충돌), 만화 페이지는 90도 단위로만 회전한다. 임의 회전이 필요하면 도형 도구의 `angle_degrees`로 개별 요소를 돌린다 |
| D-D5 | 회전·대칭은 **모든 자식의 좌표를 변환**한다. 자산 픽셀은 바꾸지 않는다 | 좌표 변환은 되돌릴 수 있고 원본 픽셀을 보존한다(D-D3과 같은 원칙). 래스터 자산을 실제로 돌리면 비가역이고, 벡터 도형은 어차피 좌표로 표현된다 |
| D-D6 | **벡터 요소의 회전은 좌표 변환이 아니라 그 요소의 `angle_degrees`에 반영한다** | 1a가 `ShapeLayer`에 `angle_degrees`를 두었다. 90도 회전한 페이지에서 도형의 좌표만 돌리고 각도를 그대로 두면 도형이 엉뚱한 방향을 본다. **이것이 D에서 가장 깨지기 쉬운 지점이다** — 1b에서 프론트와 서버의 회전 규칙이 어긋난 것과 같은 유형이다 |
| D-D7 | 이미지 삽입은 **새 래스터 레이어**를 만들고, 원본 해상도를 보존한다 | 페이지 크기에 맞춰 자동 축소하면 화질을 되돌릴 수 없다. 레이어는 페이지보다 클 수 있고, 그 일부만 보인다 |
| D-D8 | 삽입 이미지의 초기 위치는 **페이지 좌상단(0,0)에 원본 픽셀 크기로** | 커서 위치에 놓으면 드롭 지점이 스크롤에 따라 달라져 테스트가 어려워진다. 사용자가 놓은 뒤 옮긴다 |

### D-D5와 D-D6이 이 서브프로젝트의 핵심이다

페이지를 90도 돌리면 모든 자식의 좌표가 바뀐다. 자식의 종류마다 "좌표를 바꾸는
것"과 "좌표 + 방향을 바꾸는 것"이 다르다:

| 자식 | 회전 시 |
|---|---|
| 래스터 레이어 | 자산은 그대로, **자산을 놓는 좌표/변환**이 바뀐다 |
| 도형 레이어 | 폴리곤 좌표가 바뀌고 **`angle_degrees`도 바뀐다** (D-D6) |
| 텍스트 레이어 | 앵커 좌표가 바뀌고 **쓰기 방향이 바뀐다** (`WritingMode`) |
| 그룹 | 자식들을 재귀적으로 변환 |

**이 표가 곧 테스트 목록이다.** 각 종류마다 "회전 후 어디에 있어야 하는가"를
리터럴로 못 박는다.

**좌표 변환은 한 곳에서 한다.** 1a에서 `merge_pages`가 기하를 옮기면서 불변식을
깨뜨린 Critical이 있었다. 같은 실수를 반복하지 않으려면 좌표 변환을 하는 함수가
**하나**여야 하고, 모든 자식 종류가 그 함수를 지나야 한다. 종류별로 각자 변환하면
새 종류가 추가될 때 그 종류를 빠뜨린다 — 그래서 **변환을 빠뜨린 종류를 잡는
테스트**를 둔다("모든 자식 종류를 변환했는지" enumerating하는 테스트).

## 커맨드

### D1/D2 — 페이지 변형

```rust
pub async fn resize_page(
    expected_revision: Revision,
    page: EntityId,
    width: f64,
    height: f64,
    resample: bool,
) -> Result<LayerCommit, Error>

pub async fn transform_page(
    expected_revision: Revision,
    page: EntityId,
    transform: PageTransform,
) -> Result<LayerCommit, Error>

pub enum PageTransform {
    RotateClockwise,
    RotateCounterClockwise,
    FlipHorizontal,
    FlipVertical,
}
```

`resize_page`는 `width`/`height`가 유한하고 0보다 큰지 검증한다(기존 `Page::validate`와
같은 규칙). `resample`이 참이면 모든 래스터 자산을 새 크기로 리샘플한다(D-D3).

`transform_page`의 회전은 **페이지의 `width`와 `height`를 맞바꾼다.** 90도 회전은
가로·세로를 교환하므로 이것을 빠뜨리면 내용이 잘린다. 이 사실을 주석에 남긴다.

### D3 — 이미지 삽입

```rust
pub async fn insert_image_layer(
    expected_revision: Revision,
    page: EntityId,
    bytes: Vec<u8>,
    media_type: String,
    name: String,
) -> Result<LayerCommit, Error>
```

`insert_image_layer`는 `apply_raster_stroke`의 레이어 생성 분기(`project.rs:1543-1575`)를
**그대로 재사용**한다 — `RasterLayer { origin: User, name, kind }`를 만들고
`AssetRole::new("source")`로 자산을 설정한다(`project.rs:14`의 `RasterLayer as SceneRasterLayer`
별칭을 쓴다). 차이는 **자산이 이미지에서 오고 빈 캔버스가 아니라는 것**뿐이다.

**`RasterLayerKind`에 `Image` 변형을 추가해야 한다.** 현재 변형은
`{Cleanup, Paint}` 둘뿐이다(`layers.rs:18-21`, `#[serde(rename_all = "snake_case")]`).
삽입된 참조 이미지는 붓으로 그린 레이어와 구분되어야 한다 — 예를 들어 E의 톤
붙이기나 C3의 레이어 조작이 "이 레이어가 사용자가 그린 것인가"를 알아야 한다.

**변형 추가는 `revision` 규약을 따른다.** 1a·1b가 확립한 대로 enum 변형은
`u8` 태그의 하위 비트에 id가 있고, **뒤에 추가하면 기존 id가 보존된다**.
`Image`를 `Paint` 뒤에 붙이므로 기존 저장 데이터의 `Cleanup`(0)·`Paint`(1)는
그대로 읽힌다. 1b의 `ShapeFill::Gradient` 추가가 정확히 같은 작업이었고
스펙·계획·테스트가 그 규약을 이미 문서화하고 있다.

## 다른 서브프로젝트와의 관계

- **C와 좌표를 공유한다.** C의 선택 영역은 페이지 픽셀 좌표이므로 회전하면
  선택도 변환되어야 한다. **다만 선택은 저장하지 않으므로(S-D2) 회전 시
  선택을 해제하는 것이 가장 단순하다** — 계획에서 정한다.
- **1c와 자산을 공유한다.** 삽입 레이어도 `AssetRole`을 쓴다.
- **E가 D3을 쓴다.** 말풍선·소재 삽입이 같은 경로를 탄다.
- **B3(색보정)과 상호작용한다.** 삽입한 이미지 레이어도 색보정 대상인가?
  `RasterLayerKind::Image`가 B3의 "래스터 레이어만" 조건에 포함되는지
  **계획에서 확인한다** — 포함이 자연스럽다.

## 열린 문제

1. **`RasterLayerKind::Image` 추가** — 위에서 확정했다. 현재 `{Cleanup, Paint}`뿐이므로
   `Image`를 뒤에 추가하고, 기존 id가 보존되는지 라운드트립 테스트로 못 박는다.
   **이것이 D의 유일한 저장 스키마 변경이다.**
2. **페이지 밖 내용의 렌더링.** D-D2가 "남아 있다"고 정했으므로 렌더러가 페이지
   밖을 그리지 않아야 한다. 클립이 이미 그렇게 하는지 **계획에서 확인한다.**
3. **리샘플 필터.** `resample: true`일 때 어떤 필터인가 — `image`의
   `resize`는 `FilterType`을 받는다. 기본을 정해야 한다. **계획에서 정한다.**
